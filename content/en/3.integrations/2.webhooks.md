A **webhook** pushes KwikTalk events to an URL you control: incoming replies,
status changes, instance state, campaign completion.

Access: **`/admin/webhooks`** · API: `POST /api/v1/webhooks`

::u-alert{color="warning" icon="i-lucide-lock"}
Webhooks are available on the **Growth** (3 endpoints) and **Business**
(unlimited) plans. The **Starter** plan has none. See
[Pricing](/en/overview/pricing).
::

## Events

| Event | Fired when |
|---|---|
| `message.received` | An **incoming** message arrives |
| `message.status.updated` | An outgoing message's status changes (`sent`, `delivered`, `read`, `failed`) |
| `instance.connected` | A WhatsApp instance just connected |
| `instance.disconnected` | An instance disconnected |
| `instance.banned` | A number was **banned** by WhatsApp |
| `campaign.completed` | A campaign finished |
| `test` | Test event, sent from the UI |

You choose which events each endpoint subscribes to.

## Payload

Every delivery has the **same envelope**; only the `data` charge changes:

![A KwikTalk webhook payload](/images/webhook-payload.png)

| Field | Purpose |
|---|---|
| `event` | The triggering event |
| `id` | Unique UUID for the delivery — **use it to deduplicate** |
| `timestamp` | ISO 8601 timestamp |
| `instance` | `id`, `name` and `phone_number` of the related instance, or `null` |
| `data` | Event-specific payload |

::u-alert{color="info" icon="i-lucide-fingerprint"}
The `id` field is stable and unique: **store it** so you never process the same
event twice — deliveries can be **replayed**.
::

## Verify the signature

KwikTalk signs every request in **HMAC-SHA256** with the endpoint secret and
sends the result in three headers:

```http
X-KwikTalk-Signature: sha256=<hex>
X-KwikTalk-Event: message.received
X-KwikTalk-Delivery-Id: <id>
```

The signature is computed over the **re-serialised JSON**:

```php
$expected = 'sha256='.hash_hmac('sha256', json_encode($payload), $secret);
```

::u-alert{color="warning" icon="i-lucide-shield-alert"}
**Always verify the signature before handling a webhook.** Without it, anyone
can push a fake event to your endpoint. Compare in **constant time** to avoid
timing flaws.
::

You can **regenerate the endpoint secret** at any time (`regenerate-secret`) —
remember to update your receiver at the same time.

## Delivery reliability

Every attempt is logged and replayable:

| Parameter | Value |
|---|---|
| Attempts | **5** |
| Request timeout | **10 s** |
| Backoff | **1 min → 5 min → 15 min → 60 min** |
| After 5 failures | Delivery marked **`dead`** |

Delivery statuses:

| Status | Meaning |
|---|---|
| `pending` | Being sent / awaiting retry |
| `success` | Your server responded |
| `failed` | Attempt failed, retry scheduled |
| `dead` | Exhausted its attempts |

::u-alert{color="info" icon="i-lucide-rotate-ccw"}
Each delivery can be **replayed manually** from the UI (`replay`). That is the
standard procedure after maintaining your receiver.
::

## Create an endpoint

### From the UI

**Webhooks → Create**: fill in the URL, tick the events, save. Use the **Test**
button to send a `test` event and validate your receiver in real conditions.

### From the API

```bash
curl -X POST https://api.kwiktalk.app/api/v1/webhooks \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://my-server.com/hooks/kwiktalk", "events": ["message.received"]}'
```

The signing `secret` is returned at creation — keep it.

::u-alert{color="info" icon="i-lucide-key-round"}
The API lists, edits and deletes webhooks (`GET`, `PATCH`, `DELETE`
`/api/v1/webhooks/{id}`). These calls use the same
[key as message sending](/en/integrations/api-applications).
::

## Towards n8n, Make or a CRM

The [chatbot](/en/features/chatbot) **webhook mode** is different: it is used to
**reply** (your service decides the answer), whereas the regular webhook
**informs**. The two complement each other:

```
incoming message ─→ webhook (notification) ─→ your system
                  └→ chatbot webhook mode ──→ your system replies
```
