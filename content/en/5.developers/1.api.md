The KwikTalk API lets **your application** send WhatsApp messages from your number,
and follow what was sent.

Access: left menu → **API applications**

::u-alert{color="info" icon="i-lucide-lock"}
The API is included from the **Growth** plan (3 applications) and unlimited on
Business. On Starter, the menu entry does not appear — see
[Plans and quotas](/en/billing/plans).
::

## Create an API key

1. First connect the **WhatsApp instance** that will send the messages.
2. **API applications → Create an application**.
3. Give it a **name** ("E-commerce site", "CRM") and pick the attached **WhatsApp
   instance**.
4. **Copy the key shown immediately**: it is never displayed again. Only its prefix
   stays visible in the list.

::u-alert{color="warning" icon="i-lucide-key-round"}
A key can send messages from your number. Keep it server-side, never in client
code or a public repository. If it leaks, **Regenerate key** invalidates the old
one instantly.
::

Each key is tied to **one instance**. To send from two numbers, create two
applications.

## Authentication

Every request carries the key in an `Authorization` header:

```
Authorization: Bearer YOUR_API_KEY
```

Base URL: `https://<your-kwiktalk-instance>/api/v1`

## Send a message

`POST /api/v1/messages/send`

```bash
curl -X POST https://kwiktalk.example.com/api/v1/messages/send \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"to":"2250701020304","message":"Hello, your order is ready."}'
```

| Field | Type | Rule |
|---|---|---|
| `to` | string | International number, without `+`. 20 characters max. |
| `message` | string | 4,096 characters max. |

Response:

```json
{ "success": true, "data": { "message_id": 1234 } }
```

## Message history

`GET /api/v1/messages`

```bash
curl "https://kwiktalk.example.com/api/v1/messages?status=delivered&limit=50" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

| Parameter | Values |
|---|---|
| `status` | `pending`, `sending`, `sent`, `delivered`, `read`, `failed` |
| `limit` | 1 to 100 (50 by default) |
| `before` | a message identifier: returns the ones before it |

The response contains, for each message, the identifier, the recipient, the type,
the content, the status, the campaign identifier and the send dates.

## Check that a number exists on WhatsApp

`POST /api/v1/contacts/verify`

```bash
curl -X POST https://kwiktalk.example.com/api/v1/contacts/verify \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"phone_number":"2250701020304"}'
```

```json
{ "success": true, "data": { "is_whatsapp_user": true, "jid": "2250701020304@s.whatsapp.net" } }
```

The check is free in real time but costs a WhatsApp request: do not call it in a
loop on the same list.

## Rate limit

Each key has its own limit, **300 requests per minute** by default. Beyond that,
the API answers `429`. Send your messages in sequence rather than in parallel, and
respect a delay between two sends (3 to 10 seconds): that is what protects your
number.

## Errors

Every error returns a JSON body shaped like:

```json
{ "success": false, "code": "invalid_api_key", "message": "Invalid API key." }
```

| HTTP | `code` | Cause |
|---|---|---|
| 401 | `missing_api_key` | `Authorization: Bearer …` header absent |
| 401 | `invalid_api_key` | Unknown or revoked key |
| 403 | `inactive_api_key` | Application disabled |
| 403 | `instance_disconnected` | The attached instance is no longer connected |
| 422 | `send_failed` | WhatsApp refused the send (`message` holds the reason) |
| 422 | `verification_failed` | The number check failed |
| 429 | — | Rate limit reached |

## What the API does not do

Contacts, groups, templates, campaigns and chatbot management stay in the
interface. The API covers sending, history and checking a number.

## Good practice

- **One key per integration**: you can revoke one without breaking the others.
- **Log the `message_id` values**: they are what lets you match a send with a
  status in the history.
- **Handle `429` with a backoff**, not immediate retries.
- **Verify the number** before an important send: an invalid number is a failure
  that weighs on your instance's reputation.
