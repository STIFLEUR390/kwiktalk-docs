Un **webhook** pousse les événements KwikTalk vers une URL que vous contrôlez :
réponses entrantes, changements de statut, état des instances, fin de campagne.

Accès : **`/admin/webhooks`** · API : `POST /api/v1/webhooks`

::u-alert{color="warning" icon="i-lucide-lock"}
Les webhooks sont réservés aux plans **Growth** (3 endpoints) et **Business**
(illimité). Le plan **Starter** n'en dispose pas. Voir
[Tarifs](/fr/pour-demarrer/tarifs).
::

## Les événements

| Événement | Déclenché quand |
|---|---|
| `message.received` | Un message **entrant** est reçu |
| `message.status.updated` | Le statut d'un message sortant change (`sent`, `delivered`, `read`, `failed`) |
| `instance.connected` | Une instance WhatsApp vient de se connecter |
| `instance.disconnected` | Une instance s'est déconnectée |
| `instance.banned` | Un numéro a été **banni** par WhatsApp |
| `campaign.completed` | Une campagne est terminée |
| `test` | Événement de test, envoyé depuis l'interface |

Vous choisissez les événements auxquels chaque endpoint s'abonne.

## Payload

Chaque livraison a la **même enveloppe**, seule la charge `data` change :

![Payload d'un webhook KwikTalk](/images/webhook-payload.png)

| Champ | Rôle |
|---|---|
| `event` | L'événement déclencheur |
| `id` | UUID unique de la livraison — **à utiliser pour dédupliquer** |
| `timestamp` | Horodatage ISO 8601 |
| `instance` | `id`, `name` et `phone_number` de l'instance concernée, ou `null` |
| `data` | Charge propre à l'événement |

::u-alert{type="info" icon="i-lucide-fingerprint"}
Le champ `id` est stable et unique : **enregistrez-le** pour ne pas traiter deux
fois le même événement, surtout que les livraisons peuvent être **rejouées**.
::

## Vérifier la signature

KwikTalk signe chaque requête en **HMAC-SHA256** avec le secret de l'endpoint, et
transmet le résultat dans trois en-têtes :

```http
X-KwikTalk-Signature: sha256=<hex>
X-KwikTalk-Event: message.received
X-KwikTalk-Delivery-Id: <id>
```

La signature est calculée sur le **JSON re-serialisé** :

```php
$expected = 'sha256='.hash_hmac('sha256', json_encode($payload), $secret);
```

::u-alert{color="warning" icon="i-lucide-shield-alert"}
**Vérifiez toujours la signature avant de traiter un webhook.** Sans cette étape,
n'importe qui peut envoyer un faux événement vers votre endpoint. Comparez de
façon **à temps constant** pour éviter les failles de timing.
::

Vous pouvez **régénérer le secret** d'un endpoint à tout moment
(`regenerate-secret`) — pensez à mettre à jour votre récepteur en même temps.

## Fiabilité de la livraison

Chaque tentative est journalisée et rejouable :

| Paramètre | Valeur |
|---|---|
| Tentatives | **5** |
| Délai d'une requête | **10 s** |
| Backoff | **1 min → 5 min → 15 min → 60 min** |
| Après 5 échecs | Livraison marquée **`dead`** |

Statuts d'une livraison :

| Statut | Signification |
|---|---|
| `pending` | En cours d'envoi / en attente de reprise |
| `success` | Votre serveur a répondu |
| `failed` | Tentative échouée, reprise planifiée |
| `dead` | Épuisé ses tentatives |

::u-alert{type="info" icon="i-lucide-rotate-ccw"}
Chaque livraison peut être **rejouée manuellement** depuis l'interface
(`replay`). C'est la procédure standard après une maintenance de votre récepteur.
::

## Créer un endpoint

### Depuis l'interface

**Webhooks → Créer** : renseignez l'URL, cochez les événements, enregistrez.
Utilisez le bouton **Tester** pour envoyer un événement `test` et valider votre
récepteur en conditions réelles.

### Depuis l'API

```bash
curl -X POST https://api.kwiktalk.app/api/v1/webhooks \
  -H "Authorization: Bearer VOTRE_CLE_API" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://mon-serveur.fr/hooks/kwiktalk", "events": ["message.received"]}'
```

Le `secret` de signature est renvoyé à la création — conservez-le.

::u-alert{type="info" icon="i-lucide-key-round"}
L'API liste, modifie et supprime les webhooks (`GET`, `PATCH`, `DELETE`
`/api/v1/webhooks/{id}`). Ces appels passent par la même
[clé que l'envoi de messages](/fr/integrations/applications-api).
::

## Vers n8n, Make ou un CRM

Le mode **webhook du [chatbot](/fr/fonctionnalites/chatbot)** est distinct : il
s'utilise pour **répondre** (votre service décide de la réponse), là où le webhook
classique **informe**. Les deux se complètent :

```
message entrant ─→ webhook (notification) ─→ votre système
                 └→ chatbot mode webhook ──→ votre système répond
```
